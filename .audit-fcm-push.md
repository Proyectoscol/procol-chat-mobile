## Estado actual de FCM/Push

### 1. `saveDeviceDetails` (settingsActions.ts)

- El `sleep(1000)` en linea 119 es un workaround documentado para un bug conocido de `@react-native-firebase`: [issue #6893](https://github.com/invertase/react-native-firebase/issues/6893).

### 2. `findNotificationFromFCM` y `findConversationLinkFromPush` (pushUtils.ts)

**Resultado: BUGS CORREGIDOS**

Problemas encontrados:

- `findNotificationFromFCM` (linea 66 original): llamaba `JSON.parse(message.data.notification)` sin verificar si `message.data` o `message.data.notification` existian. Crash garantizado si llega un mensaje FCM con estructura diferente a la esperada.
- `findNotificationFromFCM`: no tenia `try/catch` alrededor de ninguno de los dos `JSON.parse`. Payload malformado crasheaba el handler de notificaciones.
- `findConversationLinkFromPush`: aceptaba `notification: Notification` sin posibilidad de null, pero `findNotificationFromFCM` podia devolver `null`. Si el caller pasaba null, acceder a `notification.notificationType` causaba crash.

Correcciones aplicadas:
- `findNotificationFromFCM` ahora tiene `try/catch` global y devuelve `null` ante cualquier error de parseo.
- Se agregaron guardas de null para ambas ramas (FCM v1 y legacy).
- `findConversationLinkFromPush` ahora acepta `notification: Notification | null | undefined` y retorna `undefined` si es falsy.

**Archivo afectado**: `src/utils/pushUtils.ts`

### 3. Background message handler (navigation/index.tsx, linea 37-39)

**Resultado: INCOMPLETO - requiere decision de producto**

El handler actual:
```ts
setBackgroundMessageHandler(getMessaging(), async remoteMessage => {
  console.log('Message handled in the background!', remoteMessage);
});
```

**Problema**: Para mensajes FCM de tipo `data-only` (que es como Chatwoot envia las notificaciones), cuando la app esta en background en Android, el handler se llama pero no muestra ninguna notificacion visible al usuario. El SDK de Firebase muestra notificacion automatica solo si el mensaje incluye un campo `notification` en el payload; los mensajes de Chatwoot usan solo `data`.

**Impacto**: Los usuarios en Android con la app en background pueden no recibir notificaciones visibles, aunque el device si reciba el mensaje FCM. Esto es directamente relevante para VoIP (una llamada entrante necesita despertar la pantalla).

**Recomendacion pendiente (requiere aprobacion)**: Usar `@notifee/react-native` para mostrar la notificacion manualmente dentro del `setBackgroundMessageHandler`. Requiere:
1. Cargar notifee en Android (actualmente solo se carga en iOS en `pushUtils.ts`).
2. Parsear el payload con `findNotificationFromFCM`.
3. Crear un canal Android con `notifee.createChannel`.
4. Llamar `notifee.displayNotification`.

## Preparacion para VoIP (solo documentacion - sin cambios)

### Version de Notifee

`@notifee/react-native: ^9.1.1` - version moderna, con soporte completo para Android. La API que necesita VoIP existe en esta version.

### Configuracion actual

Notifee solo se carga condicionalmente en iOS (`pushUtils.ts`, linea 7-11). En Android, la variable `notifee` queda `undefined` y todas las funciones de badge/clear son no-op. Esta es la razon por la cual no hay notificaciones locales en Android actualmente.

### Que se necesitaria para AndroidImportance.HIGH y canales de llamada

1. **Quitar el guard `Platform.OS === 'ios'`** en `pushUtils.ts` para cargar notifee en Android tambien.
2. **Crear un canal Android** con `AndroidImportance.HIGH`:
   ```ts
   await notifee.createChannel({
     id: 'calls',
     name: 'Llamadas entrantes',
     importance: AndroidImportance.HIGH,
     sound: 'ringtone',
   });
   ```
3. **Full-screen intent** para mostrar la pantalla de llamada sobre el lock screen:
   ```ts
   await notifee.displayNotification({
     android: {
       channelId: 'calls',
       fullScreenAction: { id: 'default' },
       importance: AndroidImportance.HIGH,
     }
   });
   ```

### Permisos de AndroidManifest.xml que se necesitarian para VoIP

Permisos actuales: `INTERNET`, `SYSTEM_ALERT_WINDOW`, `VIBRATE`, `READ_EXTERNAL_STORAGE`, `WRITE_EXTERNAL_STORAGE`.

Permisos adicionales necesarios para VoIP (NO implementados todavia):

| Permiso | Para que | Tipo |
|---|---|---|
| `USE_FULL_SCREEN_INTENT` | Mostrar pantalla de llamada sobre lock screen | Normal (Android 14+: solicitar en tiempo de ejecucion) |
| `FOREGROUND_SERVICE` | Mantener el servicio de llamada activo | Normal |
| `FOREGROUND_SERVICE_PHONE_CALL` | Tipo de foreground service para llamadas (Android 14+) | Normal |
| `RECORD_AUDIO` | Microfono para WebRTC | Dangerous (requiere permiso en runtime) |
| `RECEIVE_BOOT_COMPLETED` | Reiniciar el servicio tras reinicio del telefono | Normal |
| `CAMERA` | Video llamadas (opcional) | Dangerous |
| `MANAGE_OWN_CALLS` | API ConnectionService para integracion con el dialer del sistema | Normal |

### Restricciones de Expo SDK 53

- Expo SDK 53 usa React Native 0.79 con la nueva arquitectura (Bridgeless). Notifee 9.x es compatible.
- `USE_FULL_SCREEN_INTENT`: desde Android 14, las apps deben solicitar este permiso via `Settings.ACTION_MANAGE_APP_USE_FULL_SCREEN_INTENTS` (no basta declararlo en manifest). La Play Store puede rechazar apps que abusen de este permiso sin categoria de llamada.
- Expo Go no es compatible con modulos VoIP nativos; se necesita un `development build` o APK de release (ya es el flujo actual).
- Si se usa `ConnectionService` (integracion con el dialer nativo, como WhatsApp), se necesita un modulo nativo adicional (`react-native-callkeep` o implementacion propia). Esta es la mayor complejidad de VoIP.

### Estimacion de complejidad

| Componente | Complejidad |
|---|---|
| Notificacion de alta prioridad en background (Android) | Baja - 1-2 dias |
| Pantalla de llamada entrante (full-screen intent) | Media - 3-5 dias |
| Integracion con dialer del sistema (ConnectionService) | Alta - 1-2 semanas |
| WebRTC peer-to-peer | Alta - depende del backend |
| WebRTC via SFU/TURN | Muy alta - infraestructura separada |
